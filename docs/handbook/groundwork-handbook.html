SECTION 2   ·   SUBSECTION 2.1
SYSTEM ARRANGEMENT
2.1.1

INTRODUCTION.

Groundwork turns a field-service member’s text and photos into a priced quote, scheduled work, and an invoice. The model interprets intent; code identifies the caller and computes every amount (figure 2.1-1).

2.1.2

FUNCTIONAL DESCRIPTION.

iMessage, web chat, and member-forwarded email reach the assistant. Tools load the business, customer, price book, and notes. An owner or admin approves the quote; the customer signs its current revision on the link. Work is booked separately. An invoice copies the agreed quote (figure 2.1-2).

2.1.2.1

Authority boundary.

Active membership, role, suspension, and business scope are checked in code. Forwarded email may create drafts; it cannot authorize protected changes.

QUOTATION AND PHOTO SYSTEM
2.2.1

INTRODUCTION.

A priced photo locates quoted work; it does not measure it. Muse Wonder proposes scope, the member confirms photo-derived quantities, and the calculator prices the quote. SAM 3.1 supplies outlines only (figure 2.2-1).

2.2.2

FUNCTIONAL DESCRIPTION.

The tools resolve saved item IDs to rates. The calculator rounds each line to cents, adds selected rules, applies the minimum, then adjusts and taxes the result (figure 2.2-2). The PDF and photo labels reuse those amounts. A missing price normally returns “needs_owner”; a one-time total override is explicit.

2.2.2.1

Retained segmentation.

SAM masks and candidates are stored. Selecting saved outlines or drawing by hand needs no new SAM call; a box prompt or correction points request segmentation again.

SECTION 2   ·   SUBSECTION 2.3
SCHEDULING AND DISPATCH
2.3.1

INTRODUCTION.

Groundwork computes a crew’s route from booked visits, the yard, equipment, and work hours. Open slots rank days under capacity first, then added driving. Re-planning proposes changes; it does not silently move work (figure 2.3-1).

2.3.2

FUNCTIONAL DESCRIPTION.

Crew text “next”, “here”, “done”, or “running 30 late”. Tools return the stop, notes, checklist, and revised day plan. Completing a due visit’s last checklist item can mark it done. A late day or forecast risk produces a numbered proposal; an owner or admin decides, and code rechecks it (figure 2.3-2).

2.3.2.1

Drive estimate.

Drive time uses straight-line distance × road factor at town speed, rounded up to 5 minutes. No road graph or live traffic is used; unplaced addresses use a stated fallback.

SECTION 2   ·   SUBSECTION 2.4
SETUP AND OPERATING LIMITS
2.4.1

INTRODUCTION.

One Next.js deployment serves multiple businesses with Postgres records and Blob files. Eve hosts the assistant and optional page designer. Fake adapters replace delivery services, not the model or database (figure 2.4-1).

2.4.2

FUNCTIONAL DESCRIPTION.

Development needs Node, an empty Postgres database, a Meta key, and an auth secret. Migrate, provision the business, seed a trade pack, then start the app. Production also needs public file storage and scheduled jobs. The optional designer changes customer-page layout while code supplies prices and forms (figure 2.4-2).

2.4.2.1

Safe operating modes.

Use delivery fakes and BLOB_LOCAL_DIR for development photos. Production must omit fake switches and sign-in-code logging. Database tests and evals erase the database they target.
